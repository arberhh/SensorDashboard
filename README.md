# SensorDashboard

A React Native (bare CLI, TypeScript) live sensor dashboard: 500 mock IoT
sensors with simulated readings, filtering, sorting and a detail screen.

## Run

```bash
npm install
cd ios && bundle exec pod install && cd ..   # first run / after native dep changes
npm run ios          # or: npm run android
npm start            # Metro only
```

Node 22+ (see `.github/workflows/ci.yml`).

### Backend (LIVE mode)

```bash
cd server && cargo run   # http://127.0.0.1:3000: /ws for the app, /health and /sensors for curl
```

Then switch the app to LIVE. Endpoints, example clients and checks are in
[`server/README.md`](server/README.md).

## Architecture

- **Data**: `src/data/sensor_readings.json` (500 sensors) is generated by
  `scripts/genSensorData.js`. `deviationPercent` is the percent change of
  `currentReading` from the sensor's baseline.
- **Feed** (`src/hooks`, `src/context/SensorFeedContext.tsx`): one shared
  sensor feed, consumed by both screens, with two modes switched from the
  header toggle:
  - `local` (default): `useLocalSensorFeed` ticks every 5s, giving every
    sensor a new reading within ±8% of its fixed baseline and recomputing
    its deviation from that baseline. No network.
  - `live`: `useBackendSensorFeed` follows the WebSocket at `/ws` (see
    `src/config.ts`) of the Rust backend in `server/`, which sends the full
    sensor array on connect and on every tick. Without it running, this mode
    shows an error and retries every 5s.
- **Screens**: `Home` (list, TYPE filter, TREND/NAME sort) and
  `SensorDetail` (all sensor fields except `id`, plus a Similar Sensors
  list: same type, own TREND/NAME sort, rows are not pressable).
- **Pure logic** lives in `src/utils` (`sensorList`, `sensorReadings`,
  `sensorDisplay`) so it is unit-tested without rendering.
- **Theme**: all colors, font sizes, spacing and radii come from
  `src/theme/index.ts`.

## Performance notes

| Bottleneck                                                                                    | Mitigation                                                                                                                                                           |
| --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 500 rows with an update every 5s                                                              | `FlashList` cell recycling instead of `FlatList` (ARB-20); `renderSensorRow` is a module-scope function so its identity is stable                                    |
| Filtering swaps which sensors occupy visible rows, forcing fresh cell mounts under `FlatList` | Same `FlashList` migration: cells are updated, not remounted                                                                                                         |
| Filter taps competing with an in-flight scroll for frame budget                               | TYPE filter changes are deferred with `requestIdleCallback`. The live feed is deliberately not deferred, so readings never go stale                                  |
| Live deviation reshuffling a TREND-sorted list every tick                                     | The sorted id order is captured when a chip is pressed and replayed against each snapshot (`orderByIds`); row values stay live, order changes only on the next press |

### Profiling report

React commit time for each 5s live-feed tick, on the iOS Simulator (debug
build), before ARB-20 (`FlatList`) vs `main` (`FlashList`). About 35 ticks
per version, over 3 alternating 70s runs:

| Per-tick React commit time | Before ARB-20 (`18c055f`) | `main` (`2b74209`) |
| -------------------------- | ------------------------- | ------------------ |
| Median                     | 46.5 ms                   | 20.8 ms            |
| p90                        | 60.5 ms                   | 25.9 ms            |
| Max                        | 61.6 ms                   | 35.6 ms            |

The median tick takes 55% less render time. Before, a tick took roughly
three 60fps frames (16.7 ms each) of JS time; now it takes just over one.
Startup (all mount commits together) was about the same in both versions
(~199 ms vs ~189 ms, with a wide spread between runs).

These are **JS render times** from a React `<Profiler>`, not device frame
rates. They don't cover native layout or the UI thread. Debug builds
inflate absolute numbers, but both versions ran under the same
conditions. `main` also includes everything after ARB-20, so this compares
the app before and after the optimisation work, not ARB-20 alone. Filter
and sort taps weren't measured, because they need manual interaction.
Method, raw logs and how to reproduce: [`docs/profiling`](docs/profiling/README.md).

## Testing strategy

- **Unit**: `sensorList`, `sensorReadings` (including deviation maths),
  `sensorDisplay`, and the feed hooks.
- **Integration**: `HomeScreen.integration.test.tsx` drives the real
  screen through filter and sort taps.
